# 一隅食记 · Pantry Lens v0.5

当前支持 **点选食材 → 推荐三道完整食谱**：本机版由AI挑选家常菜谱／现场生成，GitHub Pages在线版使用浏览器内菜谱匹配。保留本地照片入库原型与 Apple Vision 包装 OCR。本机AI无需另填API key，使用CLI已保存的ChatGPT登录；点击推荐会将本次食材、人数、时间、偏好和忌口发送到模型服务并使用账号额度，不是离线推理。不读取库存、照片或旧聊天作为食谱输入。在线版不调用AI，不提供云后端、OCR、库存同步、Notion或提醒。

## 启动与地址

```sh
cd pantry-lens
npm start
```

需要 macOS、Node.js 20+、Xcode 或 Command Line Tools（本机已有 Swift 6.2.3）。无需 npm install。首次启动从 `native/ocr.swift` 编译本地可执行文件到 `.cache/`，不安装依赖或下载权重。

**http://127.0.0.1:4173 仅能在这台 Mac 上打开，不能用于 iPhone。** 当前服务固定绑定 loopback，没有修改网络设置、LAN 监听或开放公网。`PORT=4174 npm start` 可换本机端口。页面已编写手机响应式布局，但真机入口和截图仍待用户解锁后另行验收；本次没有创建跨设备服务。

## GitHub Pages 在线版

发布地址：**https://ads1029.github.io/pantry-lens/**。线上版使用同一界面和5000份中西式家庭餐搭配库，在浏览器内按主料、时间、人数、忌口及简单口味匹配三道，来源与隐私说明收在页尾「关于」。不调用AI、不上传食材、不使用本机Codex额度；最近一次推荐仅保存在当前浏览器。支持1–4人；少油会筛掉较多用油的菜，素食／纯素和简单排除词用于筛选，不能理解复杂自然语言。匹配不足三道会提示调整条件，忌口不会自动放宽。线上版隐藏需要本机服务的照片OCR和库存入口；本机版保留这些功能及AI推荐。

```sh
npm test
npm run build:pages
# 在已配置origin的Git仓库中，明确执行以下命令才会发布：
npm run deploy:pages
```

`build:pages` 仅将11个白名单前端文件复制到 `dist/`，使用相对路径支持 `/pantry-lens/` 子目录。`deploy:pages` 推送该静态目录到 `gh-pages` 分支，保留当前分支和暂存区，不强制推送；没有变化时不创建发布提交。GitHub Pages发布源设为 `gh-pages` 的根目录（Deploy from a branch）。`main` 保存源码；`gh-pages` 只含网站文件，包含 `.nojekyll`。不将根目录直接作为网站发布源。

`runtime/`、`.cache/`、`dist/`、依赖、环境文件与日志均不进入源码提交；发布构建不包含后端模块、凭据、请求历史、照片或库存。GitHub站点访问本身仍由托管平台处理，推荐输入不发送到服务器。上线验证需覆盖子路径资源、真实点击、刷新恢复与不足三道提示；本机模式的五秒AI实测记录不代表在线版使用AI。

## 本机食材推荐：点击后自动生成

打开本机页面默认进入「食谱推荐」，原有功能在「食材库存」中。界面仅保留必要字段，三道菜的做法直接显示；只有需补充的用料显示「另备」，来源及隐私说明放在页尾「关于」。

1. 在「选食材」中点选分类和选项，组合本次食材。预设 38 种，分为肉蛋豆类、蔬菜菌菇、葱姜调味、米面主食，包含鸡肉、猪肉、牛肉、生菜、油麦菜、蒜蓉、姜蓉等；再次点击取消，可一键清空。也可点击蒜蓉青菜／番茄鸡蛋／姜葱鸡肉／洋葱牛肉搭配，追加相应食材而不覆盖已选内容。下方文本可补充其他食材和份量，用逗号、顿号、分号或换行分隔；手填内容与选项同步，带数字份量的同名食材不重复添加。选择人数和时间；需要时展开「偏好与忌口」点选常用偏好，再点击「推荐三道」。预设是输入快捷方式，不是固定推荐结果或库存记录。
2. 点击「推荐三道」。请求保存为 `runtime/recipes/requests/<UUID>.json`。本机先按主料、人数、时间、忌口与素食偏好筛选家常菜谱库；至少有三条候选时，AI 仅从候选中挑选三个不同编号，页面提供完整做法。少于三条时才现场生成。无需回到聊天或手动复制。
3. AI 挑选使用服务内的 Codex App Server 连接，每次是独立临时任务，无聊天历史或文件环境；JSON Schema 限定可选编号，服务再次检查三个编号不同且都属于本次候选，再恢复完整菜谱。现场生成仍使用隔离的单次 CLI，采用紧凑字段和用料编号以减少输出。服务补入请求编号、来源、模式和时间，经校验原子写入结果 JSON。
4. 页面展示三道完整备选菜：用料份量、已有／需补充／基础调味、时间、人数、步骤及提示。标记明确区分「AI 挑选 · 家常菜谱库」与「AI 现场生成」。人数自动缩放；输入明确数量且单位兼容时，用料不超过该输入值。推荐不会扣减库存。
5. 失败会显示原因，可点「重试生成」。正在运行的同一请求重复重试只重新连接，不再启动一次模型调用；已成功请求重试只返回已有结果。并发上限为 1，忙时新请求返回 429。单次生成最多 3 分钟，超时终止进程；不自动重试或批量重放历史请求。

需要 Node.js 20+、可执行的 **Codex CLI**（本轮验证版本 0.159.3），以及本机有效登录。可在终端检查：

```sh
codex --version
codex login status
# 仅在未登录时执行：
codex login
```

Codex CLI 必须支持 `app-server` 和非交互 `exec`。服务启动时仅初始化连接、读取可用模型目录，不发起模型生成；连接由当前 Web 服务拥有，关闭服务时一同退出。空闲时没有推理、排队扫描、定时生成或聊天唤醒。

快速路径固定使用已实测可用的 `gpt-6-luna` / `none`，每次创建 `ephemeral` 临时任务、只读沙箱、空文件环境与工作区，禁用 shell、应用／插件、hooks、记忆、子 agent、搜索和继承的 MCP 工具。App Server 的配置接口仅提取继承 MCP 的名称以逐个禁用，原始配置值不写入项目、日志或模型输入；凭据由 CLI 自身认证机制处理，不读取或复制登录凭据文件，不将 API key 传给网页。服务不修改个人 Codex 配置。

现场生成使用 `exec --ignore-user-config --ephemeral --output-schema`，独立临时目录、固定指令文件、stdin 数据和参数数组，无 shell 拼接，保持工具禁用与只读沙箱。收到合法完整 JSON 和完成事件后即可结束本次独立进程，减少退出等待；异常退出不冒充成功。临时文件随后清理。失败只显示错误，重试需用户主动点击，不用固定结果掩盖失败。

## 耗时、适用范围与证据

当前库有 **5000 份结构化家庭餐搭配**，保留原192道，新增8种蛋白食材×20种蔬菜×10种温和烹调风格×3种主食的4800份组合，以及8份具名家常餐改编。中式和西式新增各2404份；这是组合菜谱，不宣称5000道独立经典菜或逐一试做。新搭配包含瘦肉、鱼、虾、蛋、豆腐、熟鹰嘴豆，配米饭、糙米饭、面条、全麦意面或土豆；主料优先澳洲超市常见品类，具体门店与季节库存不保证。

新增搭配不含辣椒，少量黑胡椒用于温和调味；两人份建议添加油≤5毫升、盐≤0.8克，默认350克蔬菜，并优先全谷物、非油炸做法。这是控制添加量的配方规则，不是经检测的低脂／低钠营养声称，也不是个体化健康处方。方向参考 [Australian Dietary Guidelines](https://www.eatforhealth.gov.au/guidelines/australian-dietary-guidelines-1-5)；无加盐番茄罐头可参考澳洲超市的 [商品示例](https://www.woolworths.com.au/Shop/ProductDetails/29403/val-verde-italian-tomatoes-diced)，购买时仍需核对包装、过敏原和当地供应。

展开「偏好与忌口」，可点选「中式」「西式」「少油」「素食」「纯素」，再点取消。中式／西式、素食／纯素各自互斥，少油可叠加；自定义文字收在「其他偏好」里。刷新可恢复最近提交的选项；候选按主菜家族去重，避免仅更换主食就占满三道推荐。常见英文食材名如 zucchini、capsicum、chickpeas 支持归一化。快速路径用于 1–4 人且足够候选的组合；主料、时间或忌口筛选后不足三条，及超过4人时，会走现场生成，可能超过5秒。库内烹饪时间是估计，食品以实际熟透为准。鸡肉75℃及生熟分开的注意点参考 [FSANZ](https://www.foodstandards.gov.au/business/charities/preparing-and-cooking-food)，菜谱不是专业营养方案或烹饪实测报告。

本轮三次新请求的浏览器前台点击到完整显示分别为 **4.25、4.08、3.15 秒**，后台为 **3.40、2.48、2.71 秒**。均真实调用 AI 选择三个编号，输出各23 token，未命中旧结果缓存。输入、编号对应结果和完整分段记录见 [延迟验收证据](docs/recipe-latency-evidence.json)。历史现场生成约39.7–41.7秒；不同时间样本不是严格统计A/B。三个样本不构成网络／服务端延迟SLA。

结果下方可展开「本次耗时与生成信息」。每次尝试独立保存 `runtime/recipes/metrics/<UUID>.json`：指定／服务报告模型、推理强度、传输方式、任务初始化、首个事件、真实首段文字（App Server）、模型等待与输出、JSON解析、保存、后台总时间和 token 用量。CLI 首个JSONL事件不等于首字；缺失用量保留未知。各时间段有重叠，不能直接相加，服务端排队和推理内部仍不能精确拆分。

页面每250毫秒检查一次本机进度，不重复调用AI。两帧绘制后回报本次点击计时，保存在 `display-metrics/`；每个尝试编号只接受首份成功报告。刷新只是恢复已有结果，不重新计作生成，旧尝试不能覆盖新尝试，失败不能上报显示成功。网页计时是本机客户端报告，不是服务端认证计费数据。

实现与接口：

- `src/recipes.js`：共用的输入／结果契约与业务校验。
- `src/recipe-app.js`：食材点选、提交、生成状态、检查、重试、食谱展示、刷新恢复、请求导出。
- `src/ingredient-presets.js`：常用食材／家常搭配、手填内容合并、带份量匹配和取消，沿用每次最多 30 种的上限。
- `recipe-generator.mjs`：单并发调度、快速挑选／现场生成分流、180秒限制、隔离CLI与紧凑协议。
- `recipe-catalog-expanded.mjs` / `recipe-ingredients.mjs`（原 `recipe-catalog.mjs` 保留为24道基线快照）：家常菜库、候选筛选、用料来源与已知数量上限。
- `recipe-model-worker.mjs`：服务拥有的模型连接、隔离临时任务、取消／失败清理。
- `recipe-telemetry.mjs`：JSONL计时与数值用量解析，不保存原始事件正文。
- `recipe-queue.mjs`：请求、结果与任务状态 JSON 的持久化；结果必须恰好三道不同食谱、人数相同、时间不超上限，用料和步骤齐全。损坏／错配返回 422。
- `POST /api/recipes/requests`：最多 64 KiB JSON，自动模式返回 202，后台处理该次请求。
- `GET /api/recipes/requests/<UUID>`：返回带 `job` 的 `pending` 或带结果的 `ready`。
- `POST /api/recipes/requests/<UUID>/displayed`：同源计时回报，限定当前尝试与成功结果，数值不超过10分钟；不触发模型。
- `POST /api/recipes/requests/<UUID>/retry`：显式重试失败／中断请求，成功结果保持不变；重试会替换该请求已失败或损坏的生成结果。
- 接口要求本机 Host、同源 Origin（浏览器请求）和 `X-Pantry-Local: 1`，无 CORS。不接受客户端模型名、命令、文件路径或 CLI 参数，不暴露运行目录。输出文本转义展示。

输入、忌口和结果保存在本机的 `runtime/recipes/`（忽略版本控制），浏览器仅保存最近请求 ID。点击即授权把本次输入发送给 Codex 的模型服务；不会发送照片或自动读取真实库存。结构校验不能验证烹饪效果或忌口语义，做饭前仍需核对；建议用量不代表实测库存。当前是本机单人原型，没有账户隔离、全局请求配额或自动清理，不直接当公网服务部署。

手动交接命令仍作为诊断／补救入口，数据协议见 [recipe-agent.md](docs/recipe-agent.md)：

```sh
npm run recipes:pending
npm run recipes:show -- <请求ID>
npm run recipes:complete -- <请求ID> runtime/recipes/work/<请求ID>.json
```

测试中的生成器均为合成 stub，不能当真实 AI 成功证据。真实浏览器自动试跑：土豆、胡萝卜、鸡蛋／2人／30分钟，仅点击一次，40 秒后自动显示三道推荐。请求、结果与阶段检查见 [自动生成证据](docs/recipe-auto-evidence.json) 及接力卡。原有 [demo request](docs/recipe-demo-request.json) / [demo result](docs/recipe-demo-result.json) 是此前聊天手动处理的合成输入证据，不能当本轮 CLI 自动化证据。

## 真实 OCR 操作演示

1. 在 Mac 打开本机地址，保持「本机 OCR · 真实包装标签识别」。
2. 选取 `docs/synthetic-labels.png` 可体验真实 OCR。这是明确人工生成的六包装测试标签，非用户照片、非真实包装实拍。
3. 点击「生成候选草稿」。浏览器只将所选图片发送给同一台 Mac 的本地 OCR endpoint。Apple Vision 读取文字后，临时原图自动删除，不发给外部 AI 或新服务。
4. 候选应包括嫩豆腐 300克、Rolled Oats 0.5千克、大米 2千克、Yogurt 125克、豆乳 250毫升、Apple Juice 330毫升的**包装净含量**；它们的**当前剩余数量/重量全部未知**，包括未开封标签。
5. 核对候选、原文依据和开封文字，修改名称/数量/范围或使用文字纠正。原始 OCR 文字、置信度和文字框保留；可展开查看整张图的文字。
6. 确认入库后才更新库存，重复确认不重复写入。盘点须选择已有批次并覆盖剩余量；新增购买遇同名批次须明确建立独立新批次。最后一次操作可撤销。

固定样例模式仍与照片无关，未运行 OCR；文字模式是固定格式解析，不是 AI。样例、真实 OCR、手动纠正分别标注来源。

## 实际执行证据

- `docs/synthetic-labels.png`：人工生成的中英文测试标签；生成脚本为 `test/make-labels.swift`。
- `docs/ocr-evidence.json`：真实本机 HTTP → 临时图片 → Apple Vision → 包装解析的原始结果，含输入 SHA-256、OCR 引擎、文字/置信度/文字框、六个候选、时间及边界检查结果。
- `docs/ocr-check-session.txt`：该端到端测试的实际终端输出。
- `docs/demo-session.txt`：早期固定样例的数据流演示，明确标注 fixture，与真实 OCR 证据区分。

真实 OCR 执行成功，不是仅检查框架是否可加载。第一次在受限执行沙箱内调用 Vision 时返回 `Foundation._GenericObjCError error 0`；允许本机进程执行后，实际识别成功。若在类似受限沙箱中重跑仍报此错，应如实检查执行环境；应用返回错误，不回退为假成功或固定识别结果。

## 数据与接口

- `native/ocr.swift`：本机 Apple Vision，读取指定临时图片并返回文字行、置信度、坐标。处理原图方向。只做 OCR，不检测食材、物体个数、开封外观或估重。
- `local-ocr.mjs`：编译/调用适配层，随机私有临时目录、固定内部文件名、无 shell 拼接；成功、解码失败和超时均清理临时原图。
- `server.mjs`：固定 loopback 静态服务与 `POST /api/ocr` 原始图片接口。不接受客户端文件路径或文件名作为保存路径，不提供目录读取。
- `src/ocr-parser.js`：带「净含量 / 净重 / Net weight / Net wt / Net contents / Net volume」标记的文字解析为净含量候选，附近文字作名称候选。支持 g/kg/ml/l 与克/千克/公斤/毫升/升。只读到明确品名时，净含量保留未知；营养表或裸秤数字不当作净含量。邻近名称关联是启发式，需用户核对。
- `src/providers.js`：`analyze({photos: File[], description})` 统一返回候选、来源、未知项与警告；本地 OCR、fixture、手动解析和未接入视觉 provider 分离。
- `src/core.js`：纯数据的草稿、文字纠正、幂等提交、盘点、撤销；`src/storage.js` 是可替换的 IndexedDB 原子事务适配层。尚未决定接 Notion。

批次保存名称、数量/单位/范围及来源、包装净含量、开封状态文字、存放位置、更新时间与证据。原图不持久保存；照片内容指纹用于防重，草稿只在内存。导出 JSON 含记录和撤销事件，不含照片。刷新丢失草稿；清理浏览器数据删除库存。没有备份恢复 UI、消耗扣减或跨设备同步。

防重只针对完全相同的图片字节、交易 ID 和同名提示；不能识别重拍/裁切后是不是同一批食材，需用户使用盘点并选择批次。

## 上传与安全边界

每次最多 8 张，单张 15 MiB。前端检查类型/大小；后端也执行独立大小限制、MIME 与文件签名匹配检查。支持 JPG / PNG / WebP / HEIC / HEIF，实际解码由本机 ImageIO 决定；HEIC 与真实手机照片尚未实测。解码像素上限 4000 万、单边 12000 像素，本机最多同时 2 个 OCR、单张 OCR 30 秒超时。未知格式、SVG、伪装类型、损坏图片和超限图片拒绝，不执行其中内容。

接口要求本机 Host、同源 Origin（浏览器请求）和自定义请求头，不开放 CORS；静态白名单不暴露服务端代码、native 源码、缓存二进制或任意磁盘路径。原图通过随机临时目录和 `0600` 文件处理，客户端文件名不参与路径构造。

## 检查

```sh
npm test
npm run test:ocr
```

`npm test` 当前包含 28 项检查：原有库存／OCR 与食谱契约检查，加点选／手填合并与上限、自动生成 HTTP、并发／幂等、失败／重启恢复、关闭取消、CLI 参数／隔离及超时／未安装、计时与刷新保护、紧凑用料编号、菜谱筛选、连接隔离与取消检查，以及静态匹配来源／边界、发布白名单与模块依赖检查。食谱测试使用临时目录和合成数据，不读取真实库存。`test:ocr` 实际运行 Vision，并验证六包装候选、全部剩余未知、重复提交不重复入库、错误类型 415、超限 413、损坏图片 422、跨源 403、用户路径 404、服务端文件不暴露及临时图片清理。它只读人工标签图，未用用户真实照片。

## 尚未实现

OCR 不等于无标签食材识别，不能判断遮挡的食材种类、实际个数或准确重量。开封/未开封仅来自标签文字；照片外观无法由此模块推断。普通照片没有可靠称重依据时必须保留未知，不把包装净重等同剩余。

完整食材视觉分类仍需要合适的本地模型或经授权的外部多模态 provider。目前没有发现可直接复用的已安装视觉模型；未读取密钥、未创建凭据或下载大型模型。下一步可先由用户在 Mac 选择清晰真实包装照片，验证本地 OCR 在弯曲、反光与多包装实拍上的候选质量，再决定是否需要额外视觉模型。外部 provider 的照片传输、费用与授权仍未批准。

历史 OCR 照片操作与手机真机验收尚未完成。食谱流程独立做浏览器验证，未重跑真实包装照片的浏览器操作。
